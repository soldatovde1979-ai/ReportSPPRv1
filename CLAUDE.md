## Что это за проект (коротко)

Ноутбук `RepSSPR.ipynb` — в Google Colab или локально на ПК (режим определяется сам, my-FT Т-99), — который еженедельно:
1. берёт JSON-выгрузку обращений в службу 1С-поддержки: решённые и отклонённые за период (рабочий режим — 4 недели) плюс все открытые (формат и функция выгрузки — `vygruzka-1c.md`);
2. режет данные по отчётной неделе и считает срок решения: 8 ч в рабочем дне, выходные и праздники не считаются (my-FT Т-67, Т-68);
3. размечает каждое решённое за период обращение через LLM (флаг `AI_PROVIDER`, по умолчанию `auto`: в Colab — DeepSeek, локально — OpenCoder; можно явно Gemini): тема, суть, тип по сути, оценка, риск повтора, тон, сложность, критичность, для правок — объект и причина;
4. сводит темы в группы, размечает открытые старше 30 дней (действие), критичные открытые инциденты, причины по планшетам, скрытые повторы;
5. получает от модели разбор каждого слайда в JSON: цифры — ключами метрик, номера обращений проверяет код, ошибка — повторный запрос;
6. пишет историю недель v2 (поток по типам, решения руководителя) и, при `IS_DEBUG = 1`, лог в CSV `result/logs/` (Google Sheets убран 14.10, my-FT В-27);
7. собирает HTML-отчёт модулем `src/report_v6.py` в оболочке `template_v6.html` → `Отчет по качеству W{N} ({дата}).html`.

Тот же модуль собирает макет `examples/mockup_report_v2.html` (`examples/build_mockup_v2.py` + разметка `examples/mockup_v2_ai.json`) — макет и отчёт не расходятся. Подробно — `spec.md`; схемы данных, конфиг, контракты с LLM и с шаблоном — `data.md`.

## Прежде чем менять ноутбук или шаблон

- Ячейки ноутбука — это не изолированные функции: `R`, `AI_MARKUP`, `AI_CACHE`, `RUN_LOG`, `HISTORY`, клиенты ИИ — общие переменные. Порядок ячеек не менять.
- Расчёт и вёрстка — только в модуле `src/report_v6.py`, в ноутбуке их не дублировать. Модуль — один файл: копий в других папках не держать — ноутбук берёт первую найденную копию, и копия в корне папки перекрывает `src/` (HANDOFF, разд. 0, п. 7). После правки модуля — пересобрать макет (`python3 examples/build_mockup_v2.py`) и сверить с прежним: меняться должно только задуманное.
- После правки модуля, ноутбука или шаблона — стенд самопроверки: `python3 examples/selftest/run.py` (Windows: `py examples\selftest\run.py`), около минуты, токенов 0. Без «ИТОГ: ОК» не коммитить. Стенд гоняет ноутбук целиком на подставной модели — в режиме Colab и локальном — и сверяет отчёт с макетом; качество ответов настоящей модели он не проверяет (my-FT Т-72). На GitHub стенд запускается сам — на каждом push в `main` с правкой файлов релиза (`.github/workflows/selftest.yml`, my-FT Т-73); красный крест у коммита — релиз не ставить.
- **Продуктив = ветка `main`** (my-FT Р-10). Два режима (Т-99): в Colab ноутбук открывается с GitHub, модуль и шаблон ячейка 1 скачивает с GitHub при каждом прогоне, на Диске — данные и запасные копии; локально (`run_local.bat` — сам делает `git pull` и открывает рабочую копию `run/RepSSPR.ipynb`, папку проекта передаёт `REPORTSPPR_ROOT`) — всё из папки проекта, данные в `source/` и `result/`, параметры прогона — `.env` (`env_param`, образец `.env.example`). Единый вход для пользователя — `README.md` (кнопка «Открыть в Colab» ведёт на `RepSSPR.ipynb`, имя постоянное). «Положи в продуктив» — навык `.claude/skills/prod/SKILL.md` (проверки и что сказать пользователю). Файлы релиза на Диск через подключение не загружать.
- Каждую точечную правку в коде сопровождать комментарием проекта:

  ```python
  # ----------------------------------------------------------------------
  # ЧТО ИЗМЕНЕНО: <что именно изменено>
  # ПОЧЕМУ: <зачем, что это даёт>
  # ----------------------------------------------------------------------
  ```

- Результат правок возвращать изменёнными блоками, даже если исходник передан одним файлом; к каждому блоку — что и зачем изменено. Исключение: если в модуле, файле или скрипте больше двух правок (блоков или мест) — выдавать файл целиком, с версией и списком изменений относительно предыдущей (решение 05.10.2026).
- Версии (my-FT Р-12): ноутбук — постоянное имя `RepSSPR.ipynb` (точка входа), версия — `NOTEBOOK_VERSION` в ячейке 1 и в шапке; модуль `src/report_v<МАЖОР>.py` (`VERSION` внутри), шаблон `template_v<МАЖОР>.html` (`TEMPLATE_VERSION` в первой строке); мажоры совпадают, ноутбук, модуль и стенд проверяют это кодом. Имена модуля и шаблона нигде не вписаны руками: ноутбук и стенд вычисляют их из `NOTEBOOK_VERSION`, модуль берёт мажор шаблона из своей `VERSION`, сборщик макета берёт старший `src/report_v*.py`, CI — по маскам. Минор — поднять номер внутри файла и шапку. Мажор (смена набора переменных шаблона или контракта модуля) — у всех трёх в одной выдаче: `git mv` модуля и шаблона, три версии, пересборка макета; код не править.
- Шапка ноутбука ведётся по правилам из неё самой — блок «Правила ведения шапки» в `RepSSPR.ipynb` (решение 07.10.2026): первым — таблица версий всех файлов, дальше блоки «Обновление ДД.ММ.ГГГГ» (новые сверху), в каждом перечислены все четыре файла, менялся ли он; описание — человеческим языком, без технических подробностей. Коммит без обновлённой шапки считается незавершённым.
- Имена полей выгрузки, ответа LLM и переменных шаблона — строго по `data.md`. Не придумывать новые имена, не подтверждённые кодом или данными.
- Каждый элемент отчёта (плитка, график, таблица, блок ИИ) — с говорящим названием, подписью периода и выборки и серой сноской «какую пользу даёт / какую проблему показывает».
- Известные проблемы — `spec.md`, разд. 7. Попутно не чинить без запроса, но и не повторять в новом коде: не хардкодить ключи, не копировать ячейки целиком.

## Git — только ветка `main`

Работа ведётся в одной ветке с пользователем — `main` (решение 01.10.2026, my-FT Р-4). Отдельные ветки ИИ не заводит, pull request не создаёт: изменения коммитятся и пушатся прямо в `main`. Перед началом работы — `git pull origin main`. Если среда сама предлагает или создаёт другую ветку — работать всё равно в `main` и сказать об этом пользователю.

## Секреты

Ключи API (`DEEPSEEK_API_KEY`, `GEMINI_API_KEY`, `GITHUB_TOKEN`) — только через функцию `get_secret` ячейки 1: в Colab — секреты Colab (`userdata.get`), локально — переменная окружения, затем файл `.env` в папке проекта (my-FT В-25; `.env` в `.gitignore`). Без литералов и резервных строк в коде и документах. Ключи в репозиторий не коммитить.

Исключение — провайдер opencoder (по умолчанию при локальном запуске): клиенту передаётся плейсхолдер `local`, авторизация выполняется внутри локального прокси OpenCoder (`OC_BASE_URL`, http://127.0.0.1:8787/v1); работает только на машине с запущенным прокси. Ноутбук проверяет прокси в ячейке 1 и останавливается до платных этапов. Ключ нужен только при `deepseek` и `google`.

В прошлой версии (`repsspr.py`) резервный ключ DeepSeek лежал в исходнике открытым текстом. В v4.0 литерал удалён; ключ в кабинете DeepSeek отозван (подтверждено пользователем 01.10.2026).
