# ЧАСТЬ 1. Что выяснено про модель данных 1С

## 1.1 Объекты

| Объект | Роль |
|---|---|
| `Справочник.Идеи` | Требование = обращение. Идея и требование — **один и тот же объект**, разных сущностей нет. |
| `Справочник.Карточка` | Карточка канбан-доски. Связана с требованием реквизитом `Предмет` (составной тип, в нём лежит ссылка на `Идеи`). |
| `РегистрСведений.СоответствиеСценариевТребованиям` | Измерение `Требование`. Используется как фильтр «обращение относится к сценарию». |
| `РегистрСведений.ИсторияСтатусовКарточек` | История статусов **карточек**. Поля: `Период`, `Карточка`, `Проект`, `Статус`, `Автор`, `Исполнитель`, `СрокПоСтатусу`, `Комментарий`. |
| `РегистрСведений.ИсторияИзмененияТребований` | История статусов **требований**. Поля: `Период`, `Идея`, `СтатусОбработкиТребований`, `Пользователь`, `Принадлежность`, `РазделПроекта`, `Приоритет`, `ТипТребования`. |
| `РегистрСведений.ЧасыФактПоКарточкам` | Фактические трудозатраты: измерение `Карточка`, ресурс `ЧасыФакт`. Сумма по карточке → `AmountTrud`. Измерение исполнителя — для `tab_trud`; пока выгружается только общий `AmountTrud`, имя измерения не нужно (решение 01.10, my-FT В-12). |
| `Справочник.Идеи.т1кПринадлежность` | Перечисление `т1кПринадлежность`; в выгрузку идут только обращения с принадлежностью «Поддержка». |
| `Перечисление.СтатусыТребования` | Статусы требования: Новое, Отклонено, ПереданоВРаботу, Уточнение, Перенесено, Отработано, Закрыто, ВозвратНаДоработку, УточнениеПредоставлено. |

## 1.2 Два регистра, а не один

Статусы живут в **двух разных регистрах**, и это главное, что нужно знать:

- `ИсторияСтатусовКарточек` (измерение `Карточка`) — рабочие статусы доски: `Ожидает анализа`, `Анализ`, `Уточнение`, `Разработка`, `Внутреннее тестирование`, `Проверка релиза`, **`Выполнено`** и прочие.
- `ИсторияИзмененияТребований` (измерение `Идея`) — статусы самого требования: **`Отработано`** (в интерфейсе — «Отработано, требует подтверждения»), **`Закрыто`**, **`Отклонено`**.

Запрос, который ходит только в первый регистр, не видит подтверждения пользователем — там нет ни «Закрыто», ни «Отработано». Именно на этом сломалась первая версия выгрузки.

`СтатусОбработкиТребований` — **перечисление**, поэтому сравнение идёт через `ЗНАЧЕНИЕ(Перечисление.СтатусыТребования.Закрыто)`, а не по `.Наименование` (реквизита `Наименование` у перечисления нет). Представления значений совпадают с рабочими названиями статусов, поэтому текст для выгрузки берётся как `Строка(<значение перечисления>)` — руками ничего не переписывается.

`ТипТребования` из того же регистра — это и есть тип обращения: Инцидент, Консультация, Изменение данных в системе, Права доступа, Дубль.

## 1.5 Статусы требования

Из `ИсторияИзмененияТребований`, представления перечисления:

`Уточнение`, `Отработано, требует подтверждения`, `Перенесено`, `Отклонено`, `Новое`, `Передано в работу`, `Закрыто`.

Смысл ключевых: **«Отработано, требует подтверждения»** — аналитик предложил решение; **«Закрыто»** — пользователь подтвердил или сработало автозакрытие через 3 дня; **«Отклонено»** — обращение завершено отказом. Финальные статусы взаимоисключающие: «Отклонено» и «Закрыто» не сменяют друг друга.

## 1.6 Производительность

Замеры показали:

- Вход в регистр по `Период` (фильтр `Период МЕЖДУ ...` без привязки к карточке) — **долго**, индекса по периоду нет.
- Вход по измерению `Карточка` (соединение с набором карточек) — **быстро**, исходный запрос отрабатывал за ~2 с.
- Соединение `Карточка.Предмет = Идеи.Ссылка` в исходном виде работает нормально — узким местом не является.

Вывод: набор карточек формируется первым, все обращения к регистру идут через соединение по `Карточка`, фильтр по `Статус.Наименование` внутри этого соединения.

## 1.7 Даты

- `Идеи.ДатаРегистрации` — дата регистрации обращения, **с временем**.
- `Период` регистра — с временем.
- В старой выгрузке формат `"ДФ=yyyy-MM-dd"` обрезал время, из-за чего SLA в Colab считался в нулях (39% нулевых). В новой выгрузке даты пишутся как `yyyy-MM-ddTHH:mm:ss`, пустая дата — пустая строка.

# ЧАСТЬ 2. Постановка

## 2.1 Выгрузка 1С

0. **Отбор.** Только обращения с `т1кПринадлежность = Поддержка`, без ЗИ (`ОтношениеТребованийКЦелямПроекта` не из списка ЗИ).
1. **Открытые обращения.** В выборку добавляются все открытые обращения с тем же реквизитным составом — фильтр по «Выполнено» убран. Открытое = у карточки нет даты «Выполнено» и у требования нет дат «Закрыто» / «Отклонено». Открытые идут первыми. Отсечки по году регистрации нет.
2. **Статус.** Поле `st` первым в объекте JSON. Для незавершённых — текущий статус карточки на максимальную дату истории.
3. **Подмена статуса.** Если статус карточки = `Выполнено`, в `st` пишется текущий статус требования из `ИсторияИзмененияТребований`, расшифрованный в запросе: «Отработано, требует подтверждения», «Закрыто», «Отклонено», «Новое», «Передано в работу», «Уточнение», «Уточнение предоставлено», «Перенесено», «Возврат на доработку». Если карточка не выполнена, но есть дата «Отклонено» — «Отклонено».
4. **Даты завершения.** `res` — дата статуса «Отработано, требует подтверждения»; `cls` — дата «Закрыто», а для отклонённых без выполненной карточки — дата «Отклонено». У открытых обе пустые.
5. **Период отбора.** Завершённые отбираются по дате «Выполнено» карточки **или** по дате «Отклонено» требования в диапазоне `&ДатаЗакрытия … &ДатаЗакрытияКонец`. Отклонённые вне периода не попадают никуда.
6. **Тип.** `type` = `ТипТребования` из последней записи регистра, с откатом на `ОтношениеТребованийКЦелямПроекта`.
7. **Состав полей JSON:** `st`, `id`, `reg`, `res`, `cls`, `sec`, `desc`, `sol`, `anl`, `cli`, `type`, `AmountTrud`. Даты — `yyyy-MM-ddTHH:mm:ss`, пустая дата — пустая строка.
7а. **Трудозатраты.** `AmountTrud` = `СУММА(ЧасыФактПоКарточкам.ЧасыФакт)` по карточке обращения, часы; нет записей — 0.
8. **Сверка.** Количество обращений со статусом «Закрыто» или «Отработано, требует подтверждения» должно совпасть с количеством строк старой выгрузки. **Проверено 22.09.2026: 102 + 64 = 166, совпадение по идентификаторам полное.**

## 2.2 Colab: что считается и как

1. Закрытыми для анализа считаются обращения со статусом «Закрыто» / «Отработано, требует подтверждения»; открытые и отклонённые идут только в свои слайды.
2. SLA = (дата предложенного решения − дата регистрации) / 3, поскольку в сутках 8 рабочих часов. Вычет 24 ч. и `busday_count` не применяются. На выгрузке от 22.09 медиана 7.8 ч против прежних 8.0 при 39% нулей.
3. Признак планшета — **только** слово «планшет» и его формы, проверяется по тексту во всей выгрузке, а не по разметке ИИ.
4. Возраст открытых считается от даты регистрации на дату формирования отчёта; граница «более месяца» — 30 дней.
5. Валидация в конце отчёта сверяет: сумму по статусам, число закрытых, покрытие оценками ИИ, сходимость инцидентов и открытых, сумму по типам.

## 2.3 Что осталось нерешённым

- `is_critical_incident` ИИ проставляет только закрытым обращениям, поэтому открытые инциденты в таймлайне не подсвечиваются как критичные.
- Названия групп тем модель иногда формулирует слишком широко; есть стоп-лист и второй проход на переформулировку, но жёсткой гарантии без фиксированного справочника нет.

## 2.4 Табличные части обращения (постановка, Т-54/Т-55 в `docs/my-FT.md`)

Каждая часть — **необязательное** поле-массив внутри объекта обращения, у каждой части свои колонки (описание — `docs/data.md`, разд. 10). Нет поля или пустой массив — «нет данных», ошибкой не считается: части можно добавлять в функцию по одной.

| Поле | Строка массива | Источник в 1С |
|---|---|---|
| `tab_trud` | `[исполнитель, часы]` | `ЧасыФактПоКарточкам`: `СУММА(ЧасыФакт)` по карточке и измерению исполнителя. Выгружать необязательно (my-FT В-12): пока данные не едут, блоки по исполнителям в отчёте скрыты. Сумма часов строк = `AmountTrud`. |
| `tab_status` | `[дата, кто сменил, регистр, статус]` | `ИсторияСтатусовКарточек` (`Период`, `Автор`, `Статус.Наименование`, регистр «карточка») + `ИсторияИзмененияТребований` (`Период`, `Пользователь`, `Строка(СтатусОбработкиТребований)`, регистр «требование»); все записи по обращению, по возрастанию даты. |
| `tab_sla` | `[дата, статус, секунд, пауза, дата смены]` | `т1кРасчетВремениВыполненияКарточки` по карточке (Т-74) — дополнение к нашему сроку, для сравнения (my-FT Р-9). |
| `tab_rate` | `[дата, оценка, заявитель, ответственный, комментарий]` | `шхОценкиТребований` по требованию (Т-77). |
| `tab_chat` | `[дата, автор, текст]` | `т1кПерепискаВКарточках` по карточке и по требованию; только при `ВыгружатьПереписку = Истина` (Т-75, для информации). |

Пример объекта с частями:

```json
{"st": "Закрыто", "id": "00-00006556", "…": "…", "AmountTrud": 15,
 "tab_trud":   [["Кузнецов И. И.", 12], ["Петров П. П.", 3]],
 "tab_status": [["2026-05-14T10:20:00", "Кузнецов И. И.", "карточка", "Анализ"],
                ["2026-05-16T09:05:00", "Кузнецов И. И.", "требование", "Отработано, требует подтверждения"]]}
```

Как писать в функции: после основного запроса — по одному пакетному запросу на часть, результат в соответствие «Требование → массив строк»; в цикле по `Выборка` после `AmountTrud`:

```bsl
// ЧТО ИЗМЕНЕНО: необязательная табличная часть tab_trud
// ПОЧЕМУ: трудозатраты по исполнителям (Т-54); нет строк — поле не пишется
Строки = ТрудПоТребованию.Получить(Выборка.Требование);
Если Строки <> Неопределено Тогда
	ЗаписьJSON.ЗаписатьИмяСвойства("tab_trud");
	ЗаписьJSON.ЗаписатьНачалоМассива();
	Для Каждого Стр Из Строки Цикл
		ЗаписьJSON.ЗаписатьНачалоМассива();
		ЗаписьJSON.ЗаписатьЗначение(Строка(Стр.Исполнитель));
		ЗаписьJSON.ЗаписатьЗначение(Стр.Часы);
		ЗаписьJSON.ЗаписатьКонецМассива();
	КонецЦикла;
	ЗаписьJSON.ЗаписатьКонецМассива();
КонецЕсли;
```

Для этого в итоговую выборку нужно добавить `Идеи.Ссылка КАК Требование`. `tab_status` пишется так же, дата — через `ДатаВJSON`.

## 2.5 Ссылка на обращение (постановка, Т-57)

Необязательное поле `url` в объекте обращения — чтобы номер в отчёте открывал карточку.

1. В итоговую выборку добавить `Идеи.Ссылка КАК Требование`.
2. В цикле после `AmountTrud`: `ЗаписьJSON.ЗаписатьИмяСвойства("url"); ЗаписьJSON.ЗаписатьЗначение(ПолучитьНавигационнуюСсылку(Выборка.Требование));` — получится `e1cib/data/Справочник.Идеи?ref=…`.
3. Открывается тонким клиентом (решение 01.10, my-FT В-13). Ноутбук ничего не достраивает: берёт `url` как есть и делает из номера обращения ссылку с этим адресом.

Нет поля — номер в отчёте остаётся текстом, ошибки нет. Сделано в v1.5.

## 2.6 Код сотрудника (постановка, Т-69)

Необязательные поля `cli_id` и `anl_id` в объекте обращения — код инициатора и код ответственного.

Зачем:
- один человек приходит в двух написаниях (в выгрузке 29.09 — 2 человека: «Mesrop Eloyan» и «Элоян Месроп», «Olga I Malina» и «Малина Ольга»), топы инициаторов делятся;
- по коду отчёт может отправлять во внешний ИИ «Аналитик 7» вместо ФИО и подставлять ФИО обратно — персональные данные не уходят в модель.

1. v1.5: `cli_id` / `anl_id` = `Строка(Ссылка.УникальныйИдентификатор())` — работает для любого типа ссылки, без обращения к реквизиту `Код`; пустая ссылка — поле не пишется.
2. В отчёте остаются ФИО; идентификаторы — для склейки написаний и для ИИ (my-FT Т-69, чат 05.10).

Нет поля — отчёт сравнивает по ФИО, как сейчас; ошибкой не считается.

## 2.7 Отбор и полнота частей (v1.5)

- Какие обращения попадают в выгрузку — как раньше (п. 2.1): решённые и отклонённые за период плюс все открытые.
- По каждому попавшему обращению части и поля идут **целиком, за всю историю**, без отсечки по дате. Неделю режет ноутбук при расчёте.
- `parent` — код главного требования из `т1кСвязанныеТребования`; связь указывается примерно в 70 % случаев — помощь поиску повторов, не замена.
